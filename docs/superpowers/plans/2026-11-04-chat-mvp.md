# Direct Chat MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the approved production-quality Persian/RTL two-user chat with listing references, idempotent text sending, blocking, unread/Seen state, and real polling on the existing Axum/MariaDB/Nuxt stack.

**Architecture:** Add one additive migration and two focused API modules: `conversations` owns canonical pairs, metadata, Inbox synchronization, and block hooks; `messages` owns sending, idempotency, message keysets, and high-water reads. The web uses client-only private routes and route-split composables/components, with no Shell polling or optimistic mutation. Real MariaDB integration tests and separate-browser-context Playwright journeys are the behavioral gates.

**Tech Stack:** Rust 2021, Axum 0.8, runtime `sqlx`/MariaDB 11, chrono/ULID and the existing fixed-window limiter; Nuxt 4/Vue/TypeScript, native `$fetch`, Playwright/Chromium, axe/Lighthouse. No new runtime dependency or external service.

**Spec:** `docs/superpowers/specs/2026-11-04-chat-mvp-design.md`

**Branch:** `arena/c2c8a31c-shabdar` only. Never rename it, force-push, open a PR, merge, or close a PR without fresh explicit user authorization.

## Global Constraints

- One canonical unordered user pair has one conversation; a listing is optional per-message context, never conversation ownership.
- Preserve historical migrations and national data: 31 provinces, 1,547 cities, Rasht city ID 1. Add only `0014_direct_chat.sql`.
- Preserve the current Rust 1.85 floor and locked dependency policy. Runtime SQL only; no `sqlx` compile-time macros and no UUID crate.
- Message body: trimmed, 1–1000 Unicode scalar characters, plain text, controls rejected except `\n`. `client_message_id` is a canonical UUID-shaped string.
- Sending allowance: 60 validated requests per user per 600 seconds, including idempotent replays; `MESSAGE_USER_LIMIT` and `MESSAGE_USER_WINDOW_SECS` configure it. Keep the limiter process-local and document the single-replica limitation.
- Inbox default/max page: 20/50. Message default/max page: 30/50. Never use offset pagination.
- Synchronization `updated_at` changes only on real mutations and never controls Inbox recency order. A server `sync_cursor` snapshot is `(max_updated_at, 0)`, so the next poll includes every row at that timestamp; temporary forward scan cursors use the actual `(updated_at, id)` and strict `>` comparison. Clients never manufacture either cursor.
- Thread polling: 10 seconds. Inbox polling: 30 seconds. No overlap; pause hidden/offline; resume from confirmed cursors.
- Read only through the latest actually rendered message. No per-message mass `read_at` writes and no Seen while reading older history.
- Browser mutations are confirmed-response-only. Preserve draft, client ID, confirmed items, and cursors on failures. No fake message, delivery, notification, unread reset, block state, or Seen.
- Private chat responses, including errors, are `Cache-Control: private, no-store` and `Vary: Cookie`. Chat SSR HTML contains no private conversation/message payload and routes are `noindex, nofollow, noarchive`.
- Public Home/Detail SSR remains immediate. Chat code stays out of public/shared chunks; admin code stays out of public chunks. Conversation-start logic loads only on contact intent or `contact=1` continuation, not with ordinary initial Detail. The absolute 100,000-gzip-byte route ceiling and all existing budgets remain unchanged.
- Inbox/message pages use set-based joins/derived tables for listing references, read state, and unread counts; do not introduce per-row N+1 queries. Preserve the specified indexes and inspect the real query plan if a gate shows regression.
- Preserve RTL, keyboard/focus behavior, light/dark, reduced motion, 44px targets, 375/768/1024/1440 layouts, existing comment/report behavior, and all 116 current Playwright tests.
- Primary tests use the real application and MariaDB. Route interception is allowed only for failure/delay/legal-duplicate injection; never replace the chat stack with mocks.
- A queued/in-progress CI run, formatting-only run, typecheck, build, or inspection is not behavioral evidence. Inspect final job/test conclusions and actual artifacts.
- GitHub Actions is canonical where local Cargo/MariaDB/Chromium is unavailable. Do not claim a locally skipped DB suite passed.

## Review Focus

These five input classes receive explicit tests in the owning task; they are not left to implementation judgment.

1. **Mutable Inbox synchronization:** a Read/block/message arriving between forward pages must be seen now or on the next poll, without reordering by `updated_at`; Task 5 pins the snapshot/scan cursor contract and Task 6 exercises it in a browser.
2. **Lost success followed by block or edited retry:** an existing idempotent message returns its original row without creating anything, while changed content conflicts safely; Tasks 3 and 8 pin server and browser behavior.
3. **Unicode/storage boundaries:** Persian, emoji, multiline, 1000/1001 scalars, NUL/CR/control input, and long unbroken text must validate and render without truncation or execution; Tasks 3 and 8 own these cases.
4. **Circular FK and destructive fixtures:** `conversations.last_message_id` and `messages.conversation_id` must migrate cleanly and every scratch reset must restore FK checks; Task 1 owns the empty-schema and repeated-reset proof.
5. **Redirect/route races and stale responses:** malformed or encoded external `next` values must not escape the origin, and a late poll/send response must not mutate a different conversation or lose a draft; Tasks 7 and 8 own the browser journeys.

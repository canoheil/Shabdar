# REST API Proposal

> **خلاصه فارسی:** API نسخهٔ اول به‌صورت REST زیر مسیر `/api/v1` طراحی می‌شود. مسیرهای عمومی بدون ورود قابل استفاده‌اند؛ عملیات شخصی و مدیریتی به نشست معتبر نیاز دارند. ورود با کد یک‌بارمصرف پیامکی انجام می‌شود و جزئیات نهایی امنیت، محدودیت درخواست و شکل دقیق خطا باید پیش از پیاده‌سازی تثبیت شوند.

## 1. Conventions

- Base path: `/api/v1`; JSON request/response, UTF-8; Persian text preserved.
- Cookie-based opaque session recommended for SSR/browser: `HttpOnly`, `Secure` in production, `SameSite=Lax`, CSRF protection for state-changing requests. Do not put bearer/session secrets in local storage. Exact session strategy remains an implementation decision.
- Public identifiers, never database sequence IDs, appear in public API payloads. Use `Authorization` only for trusted server-to-server integrations if needed.
- Dates are ISO-8601 UTC. Prices are integer `price_toman`; never use floating point.
- Paginated lists return `{ data, page: { next_cursor, has_more } }`; enforce bounded page size. Stable cursor shape is opaque.
- Standard error: `{ error: { code, message, fields? }, request_id }`. Avoid revealing whether an arbitrary phone number has an account.
- Idempotency should be considered for publish/payment operations; no payment endpoint exists in MVP.
- Authenticated endpoints require an active user session unless marked otherwise. Admin routes require an admin role, not merely a hidden URL.

## 2. Authentication and profile

| Method | Path | Auth | Request / response summary |
|---|---|---|---|
| POST | `/auth/otp/request` | Public, rate-limited | `{ phone, purpose: "login"\|"register" }` → `{ challenge_id, expires_in_seconds, resend_after_seconds }`. Generic response prevents account enumeration; actual delivery errors are safe/generic. |
| POST | `/auth/otp/verify` | Public, rate-limited | `{ challenge_id, code }` → sets session cookie; returns `{ user, is_new_user }`. Six digits; single-use, expiry, attempt limit. |
| POST | `/auth/logout` | User | Invalidates session and clears cookie → `{ ok: true }`. |
| GET | `/me` | User | Current minimal profile and capabilities. |
| PATCH | `/me` | User | `{ display_name? }` → updated profile. Phone change is out of MVP; if added, require re-verification. |

The UI implements separate Login and Register entry flows, with editable phone number before requesting OTP. Server must not trust client-provided `is_new_user` or purpose to grant privileges; account creation is controlled by verified phone and registration policy.

## 3. Public discovery and listings

| Method | Path | Auth | Request / response summary |
|---|---|---|---|
| GET | `/listings` | Public | Query: `q`, `category`, `city`, `province`, `min_price`, `max_price`, `sort=newest\|price_asc\|price_desc`, `cursor`, `limit`. Returns listing cards and cursor. “Popular” withheld until metric is decided. |
| GET | `/categories` | Public | Active category tree including Persian names and slugs. |
| GET | `/locations/provinces` | Public | Province list. |
| GET | `/locations/cities?province=…` | Public | City list for a province. |
| GET | `/listings/{slug}` | Public | Listing detail, public seller summary, image keys/URLs, category and city. Hidden/draft listings return not found to non-owners. |
| GET | `/sellers/{public_id}` | Public | Minimal seller profile and active listing page; omit phone and precise location. |
| GET | `/sitemap/listings` | Public | Optional paginated sitemap source if sitemap XML is generated by Nuxt; returns eligible canonical URLs and modification dates. |

Listing card shape proposal: `{ id, slug, title, price_toman, price_type, city, province, category, cover_image, published_at, favorite? }`. Public queries return active, non-deleted and published listings only. Filter semantics and Persian full-text behavior require product decisions and integration tests.

## 4. User listings, favorites and uploads

| Method | Path | Auth | Request / response summary |
|---|---|---|---|
| POST | `/listings` | User | Create draft or pending listing from `{ category_id, city_id, title, description, price_toman?, price_type, location? }` → listing. Publication/moderation policy TBD. |
| PATCH | `/listings/{public_id}` | Owner | Update editable fields; state transition validated server-side → listing. |
| POST | `/listings/{public_id}/publish` | Owner | Request publication/moderation → current listing state. |
| POST | `/listings/{public_id}/mark-sold` | Owner | Mark active listing sold. |
| DELETE | `/listings/{public_id}` | Owner | Soft-remove/archive own listing; response `{ ok: true }`. |
| GET | `/me/listings?status=all\|active\|sold&cursor=…` | User | Seller dashboard listing summaries and statuses. |
| POST | `/uploads` | User | Multipart image upload, strict size/count/type limits and image validation → temporary/owned storage key and dimensions. |
| DELETE | `/uploads/{public_id}` | Owner | Delete unused upload; final ownership and orphan cleanup policy TBD. |
| PUT | `/me/favorites/{listing_id}` | User | Add favorite; idempotent → `{ favorited: true }`. |
| DELETE | `/me/favorites/{listing_id}` | User | Remove favorite → `{ favorited: false }`. |
| GET | `/me/favorites?cursor=…` | User | Favorite listing cards. |

Uploads use a storage abstraction; current adapter writes to local disk and returns application-mediated or safely configured URLs. Never accept arbitrary filesystem paths from clients.

## 5. Conversations and notifications

| Method | Path | Auth | Request / response summary |
|---|---|---|---|
| POST | `/listings/{public_id}/conversations` | User | Start/reuse conversation with listing seller; reject self-contact → `{ conversation }`. |
| GET | `/me/conversations?cursor=…` | User | Conversation summaries, listing snippet, other participant, latest message, unread state. |
| GET | `/conversations/{public_id}/messages?before=…&limit=…` | Participant | Chronological paginated messages. |
| POST | `/conversations/{public_id}/messages` | Participant | `{ body }` → created message; validate length, rate-limit, moderation/report policy. |
| POST | `/conversations/{public_id}/read` | Participant | Mark messages received up to cursor as read → `{ ok: true }`. |
| GET | `/me/notifications?cursor=…` | User | Notification inbox page. |
| POST | `/me/notifications/{id}/read` | User | Mark own notification read. |

MVP can poll for new messages; WebSocket/SSE and push are deferred until latency and load requirements justify them. Enforce conversation membership on every operation.

## 8. Admin API

Separate `/api/v1/admin` namespace and separate frontend shell; enforce role authorization and audit every mutation.

| Method | Path | Auth | Request / response summary |
|---|---|---|---|
| GET | `/admin/listings?status=pending&cursor=…` | Admin | Moderation queue. |
| POST | `/admin/listings/{public_id}/approve` | Admin | Approve and publish with audit event. |
| POST | `/admin/listings/{public_id}/reject` | Admin | `{ reason }` → reject with reason/audit event. |
| POST | `/admin/listings/{public_id}/remove` | Admin | Remove listing with reason. |
| GET | `/admin/users?query=…&cursor=…` | Admin | Restricted user search; do not expose OTP secrets. |
| POST | `/admin/users/{public_id}/suspend` | Admin | `{ reason }` and audit record. |

Admin capabilities are intentionally narrow for MVP; ticket management, ad inventory and billing are future endpoints.

## 9. API questions before implementation

Decide session/CSRF design, OTP provider and resend/attempt limits, moderation state transitions, file-size/image formats, listing and slug URL contract, guest favorite behavior, exact search/sort semantics, notification delivery, and admin role policy. No endpoint listed here constitutes an approved payment or ad-booking contract.
